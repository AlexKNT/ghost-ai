## Architecture Decisions

- Trigger.dev tasks live in `src/trigger/` (configured by the existing `trigger.config.ts` `dirs: ["./src/trigger"]`). The design task is at `src/trigger/design-agent.ts`, not `trigger/design-agent.ts`.
- The canvas storage document is owned by `useLiveblocksFlow` (from `@liveblocks/react-flow`): root key `flow` → a LiveObject holding `nodes` and `edges` LiveMaps keyed by id, with each node/edge a LiveObject whose `data` is a nested LiveObject. Server-side writes (the design agent) mutate this same document with `liveblocks.mutateStorage`, which is the collaborative flow — no parallel state. It is **not** declared on the global `Liveblocks` interface, because that would make `initialStorage` a required `RoomProvider` prop even though the flow hook initializes storage on connect.
- Liveblocks storage types must be **type aliases**, not interfaces (LSON's index signature is not satisfied by interfaces). `types/canvas.ts` `CanvasNodeData` / `CanvasEdgeData` are aliases for this reason.
- AI SDK v7: use `generateText` with `Output.object({ schema })` (exported as `Output` from `ai`) and read `result.output`. `generateObject` still exists but is deprecated.
- Trigger.dev's esbuild build resolves the project's `tsconfig.json` path aliases, so `@/...` imports work inside `src/trigger/` (verified with a throwaway esbuild bundle).
- The Liveblocks `LiveblocksProvider` + `RoomProvider` pair lives in `WorkspaceShell`, not `CanvasWrapper`. The room-scoped AI sidebar needs the same room connection as the canvas, and a second provider would create a second client + WebSocket and make the user appear twice in presence. `CanvasWrapper` renders inside that provider and now only owns `ErrorBoundary` / `ClientSideSuspense` / `ReactFlowProvider`.
- `ai-status-feed` is the single source of truth for "AI is working" in a room. The sidebar reads it with `useFeedMessages(AI_STATUS_FEED_ID)` and the design agent writes it with `liveblocks.createFeedMessage` — no local or parallel realtime state. Verified against the live API that reading a feed which does not exist returns `{ data: [] }` instead of erroring, so subscribing on mount (before any run has published) is safe; the client also calls `createFeed` once so the feed exists before the first run.
- `ai-chat` is a second, independent room-scoped feed built on the same Liveblocks feed API — never a parallel realtime system. The two feeds have opposite reading rules: status is latest-only (`selectLatestAiStatus` ranks by `updatedAt ?? createdAt`), while chat keeps the whole conversation in order (`selectChatMessages` ranks by the producer-set `timestamp`, tie-broken by the server `createdAt`). Both validate payloads with Zod before anything renders, and both are read-write from the client because `session.FULL_ACCESS` (`["*:write"]`) covers the `feeds` resource.
- Chat authorship is stored as the sender's presence display name (`useSelf().info.name`) because `FeedMessage` carries no author metadata; the sidebar treats a message as "mine" when the name matches. Role is persisted (`user` / `assistant`) so AI-authored replies can be added later without a schema change — no replies are generated yet.
- Run tracking is the **submitter's** job. `hooks/useDesignRun.ts` calls `POST /api/ai/design` and then `POST /api/ai/design/token`, keeps `{ runId, accessToken }` in local state, and subscribes with `useRealtimeRun(runId, { accessToken, enabled, id: runId })`. Everything else in the room learns about the run from `ai-status-feed`, which is why the token never leaves the submitter's browser and why no run id needs to be broadcast.
- `useRealtimeRun` must always be called with `enabled: false` while there is no token: `useApiClient` throws during render when no access token is available. The subscription is also keyed by the run id (`id: runId`), so clearing `runId` after the outcome is delivered clears the finished run's SWR state instead of leaking it into the next run.
- A run's outcome is published to `ai-chat` as an `assistant` message by the submitter, exactly once (`deliveredRef` in `hooks/useDesignRun.ts` guards both the terminal-status effect and the subscription-failure effect). Terminal detection is `isTerminalDesignRunStatus(run.status)` — never `finishedAt`, which arrives a beat later — and the message text comes from `describeDesignRunOutcome` (pure, unit-tested).
- The AI Architect panel is `<TabsContent keepMounted>`: Base UI unmounts inactive panels by default, which would have dropped the run subscription (and the pending completion message) whenever the user looked at the Specs tab. Tailwind v4's preflight sets `[hidden] { display: none !important }`, so the kept-mounted panel's `display: flex` classes cannot defeat the `hidden` attribute.
- `--accent-green` (`#62C073`) and `--accent-green-text` (`#0F2E18`) are UI tokens now — the same pair the canvas palette uses for its green nodes — so the spec's green accent never has to be written as a raw hex in a component.
- Both AI routes derive project access from `roomId` and never read a client-supplied project id. The room id *is* the project id in this app (`checkProjectAccess(roomId, identity)` is what `/api/liveblocks-auth` and `/editor/[roomId]` already do), and the Zod request schema strips unknown keys, so a `projectId` in the body is ignored rather than trusted.
- Run-scoped Trigger.dev tokens are issued from one place: `lib/run-token.ts` → `issueRunTokenForOwner(userId, runId)`, which looks up the `TaskRun` row, requires `userId` to match, and returns `null` otherwise. Both token routes are thin handlers over it, so the ownership check cannot drift between them. Tokens expire after 1 hour.
- `generate-spec` is a `schemaTask` with `specGenerationPayloadSchema`, so the spec's "validate input with Zod" requirement is enforced at the Trigger.dev boundary as well as in the route: the task body only ever sees parsed data, and the payload carries the `projectId` the server resolved, never one from the client.
- The spec task consumes `nodes`/`edges`/`chatHistory` from its payload instead of reading Liveblocks storage. A spec describes what the user sees, the task mutates nothing, and `roomId` is used only to publish progress to `ai-status-feed` — the design agent remains the only task that reads and writes the room.
- `lib/spec-generation.ts` holds prompt construction and output normalization free of Trigger.dev and Liveblocks imports, so everything the model is shown (and everything that comes back) is pure and unit testable. Same reason `types/tasks.ts` owns the spec schemas: routes and tasks both import the one definition.
- `getNodeColorName` (in `types/canvas.ts`) resolves both a palette name and a stored fill hex to the palette name. `lib/design-plan.ts` and the spec prompt builder both use it, so the hex→name rule the model sees exists once instead of twice.
- Spec artifacts are stored the same way canvas snapshots are: the Markdown goes to Vercel Blob (private store) and only the reference goes to Postgres (`ProjectSpec.filePath`), never the content. Reads go through `get(url, { access: "private", useCache: false })` — a bare `fetch()` of a private blob returns 403.
- A spec's id is generated in `saveProjectSpec` (not by the database default) because the same id names both the blob path `specs/{projectId}/{specId}.md` and the `ProjectSpec` row, so the file and the record always resolve to each other. The upload happens first, so a failed upload leaves no row; the pathname is unique per spec, so a retry can never overwrite an earlier document.
- The generated document is persisted inside the `generate-spec` task, not by a follow-up client call: persistence is server-side work on an artifact the task just produced, and a client-driven save would have needed frontend logic (explicitly out of scope for feature 28) plus a second failure mode where a spec exists in the run output but nowhere else.
- `trigger.config.ts` uses `prismaExtension({ mode: "modern" })` from `@trigger.dev/build/extensions/prisma`. That is the documented setup for Prisma 7 with the `prisma-client` provider and a driver adapter: it marks `@prisma/client` external (an unreduced esbuild bundle inlines ~11 MB of Prisma runtime) while the generated TS client in `app/generated/prisma` still bundles. The client must be generated before deploying (`npx prisma generate`), and deployed runs now need `DATABASE_URL` and `BLOB_READ_WRITE_TOKEN` in the Trigger.dev dashboard alongside the existing keys.
- Spec download filenames are derived, not stored: `specFilename(projectName, createdAt)` → `<project-slug>-spec-<yyyy-mm-dd>.md`. The record keeps only the blob reference, and the slug is restricted to `[a-z0-9-]` so the value is always safe in a `Content-Disposition` header.
